The GraalPy Control Panel provides a read-only diagnostics view for applications that use
https://docs.micronaut.io/latest/guide/#python[Micronaut for Python], the GraalPy integration built into Micronaut
Core since Core 5.2.0.

To add the GraalPy panel, add the following module as a development-time dependency:

dependency:io.micronaut.controlpanel:micronaut-control-panel-graalpy[scope=developmentOnly]

Your application must still include the Core Python integration:

dependency:io.micronaut:micronaut-context-python[scope=implementation]

dependency:io.micronaut:micronaut-inject-python[scope=annotationProcessor]

`micronaut-inject-python` generates the Java bridge stubs that the panel inventories, from the Python sources under
`micronaut.python.source.root`. Applications that run Python `asyncio` on the Netty event loop also add
`io.micronaut:micronaut-context-python-netty`.

The panel is available when Control Panel is enabled and a `PythonContextExecutor` bean is present, which is the case
whenever `micronaut-context-python` is on the classpath and `micronaut.python.enabled` is not `false`. It does not
require any Python bean to exist; in that case it shows an empty state.

You can disable the panel with:

[configuration]
----
micronaut:
  control-panel:
    panels:
      graalpy:
        enabled: false
----

=== Python Beans

The panel lists the bean definitions generated by `micronaut-inject-python`, matched by the
`@PythonModule` and `@PythonClass` annotations Core adds to them. For each one it shows the bean name, the generated
Java bridge type, whether it is backed by a Python module or a Python class, the Python identity (module name, package
name, display name and nested member names), the scope and qualifier, the bridge method signatures, and an
instantiation state observed without creating the bean.

Beans annotated with `@ContextPooled` are shown with the scope `Prototype (@ContextPooled)` and the state
`Per pooled context`. `@ContextPooled` is declared with `RetentionPolicy.CLASS`, so Micronaut records only its
`@Prototype` meta-annotation in the bean definition metadata; a prototype-scoped Python bean is therefore reported as
context-pooled.

Core's Python annotations are `@Internal`, so the panel never references them at compile time: it matches them by
fully qualified name through `AnnotationMetadata`. If a future Core release renames them, the panel shows the
"No Python bean metadata detected" empty state instead of failing.

This inspection uses annotation and method metadata only. It does not call `BeanContext.getBean(...)`, inject a Python
bean, or invoke any generated bridge method.

=== Context Pool

The panel renders the snapshot returned by `PythonContextExecutor.statistics()`: whether pooling is enabled and
whether the pool is closed, the target size, the pooled, idle and event-loop context counts, and the borrow and wait
counters. It reads the same data Core exposes at `/pythonpool`, but in-process, so it works without
`micronaut-management`. When the `/pythonpool` endpoint bean is present, the Runtime Notes tab links to it and points
out that it is sensitive by default.

Two hints from the Micronaut for Python documentation are surfaced automatically:

* waits that keep growing, with the longest wait approaching `micronaut.python.pool.warn-wait`, usually mean the pool
  is too small;
* every pooled context sitting idle means the pool is larger than the workload needs.

The same tab shows the pool, asyncio and Python configuration values, and the polyglot engine implementation and
version when Core has already created an engine. The panel never creates an engine or a context to find that out, so
the engine row can legitimately read `Unknown`.

The pool section distinguishes three non-nominal states: pooling `Disabled`, a `Closed` pool, and `Unavailable`
statistics, which means the executor bean exists but did not report a snapshot. In every case the configuration values
are still shown and the page still renders.

=== Configuration

The configuration tab shows `graalpy.context.options`, `graalpy.context.host-class-lookup`, the *names* of the
`graalpy.context.environment` variables, and the `GraalPyContextCustomizer` implementations registered through
`ServiceLoader`.

Environment variable values are never rendered, and option values whose key contains `token`, `secret`, `password`,
`key` or `credential` are masked. Customizers are listed by provider type only: the panel never instantiates them and
never calls `customize(...)`.

An empty host class lookup list means host class lookup is unrestricted, which the panel states explicitly rather than
leaving the section blank.

=== Python VFS Metadata

The panel probes classpath resource roots for a `fileslist.txt` describing the packaged GraalPy virtual filesystem, in
this order:

. `META-INF/GRAALPY-VFS/micronaut-application`, where Micronaut Core packages application Python sources;
. `org.graalvm.python.vfs`, the layout used by the standalone GraalPy Maven and Gradle build plugins;
. any additional roots configured with `micronaut.control-panel.panels.graalpy.vfs-roots`.

[configuration]
----
micronaut:
  control-panel:
    panels:
      graalpy:
        vfs-roots:
          - META-INF/GRAALPY-VFS/my-library
----

When metadata is present the panel shows which root matched, sanitized classpath resource labels, and a capped,
searchable list of packaged paths grouped by area. `micronaut-context-python` packages its own runtime sources under
the core application root, so this section is normally populated even before an application adds Python sources of its
own.

The panel reads only `fileslist.txt`. It does not read the listed Python files, package contents, package indexes, or
local filesystem paths, and it never displays absolute paths. If the metadata is too large or a resource is
unreadable, the panel shows partial data with a warning instead of failing the whole page.

When nothing is found, verify that your build packaged the Python sources: Core's annotation processor writes the
application VFS during compilation, and the standalone GraalPy build plugins write `org.graalvm.python.vfs`.

=== What The Panel Does Not Do

Rendering the panel never:

* borrows a pooled context or calls `PythonContextExecutor.withContext(...)`;
* evaluates Python or calls a generated bridge method;
* creates a polyglot `Engine` or `Context`;
* instantiates a `GraalPyContextCustomizer`;
* reads any file listed in the VFS metadata.

=== Threading Notes

Every GraalPy context has its own global interpreter lock, and the context pool exists to reduce GIL contention across
concurrent requests. Context pooling and `@ContextPooled` are documented as experimental. Python must not run on
virtual threads; keep Python-backed beans on a platform-thread executor as described in the Micronaut for Python
documentation.
